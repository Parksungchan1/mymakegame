# 디자인 담당 진행 기록

## 2026-07-31 — 캐릭터·아레나 1차 아트 (임시 도형 → 실제 디자인)

### 왜 했나
그때까지 화면에 있던 건 **흰 캡슐 + 검은 박스(얼굴)** 하나와 **회색 상자 3개가 놓인 빈 방**이었다.
전부 개발이 동작 확인용으로 세운 플레이스홀더였고, 기획서가 정한 그림과 아무 관계가 없었다.

기준으로 삼은 기획서 문장:
- 10행 「맵: **거대한 원룸 한 칸**, 소형 인간들이 싸움」
- 10행 「캐릭터/속도는 **멧챠 카멜레온풍**」 (작고 날쌘)
- 12행 「이펙트: **마법봉으로 마법 쓰는 연출**」
- 61~69행 ✅결정됨 「카메라 **고정 각도**」 (yaw 0°, pitch -32°, 7m)

고친 파일은 `game/scenes/Player.tscn`, `game/scenes/Arena.tscn` **둘뿐**이다.
스크립트·기획 문서·STATUS 는 건드리지 않았다.

### 1. 캐릭터 (`game/scenes/Player.tscn`)

**2등신 마법사.** 캡슐 하나 → 머리·몸통·팔·다리·발·모자·망토깃·눈·마법봉 구성.

| 부위 | 의도 |
|---|---|
| 머리 크게 / 몸통·팔다리 짧게 | 위에서 -32°로 내려다보는 화면에서는 머리가 화면의 대부분이다. 2등신이라야 "사람"으로 읽힌다. |
| 고깔모자(앞으로 10° 기울임) | 마법봉과 짝을 이루는 실루엣. 기울여서 앞뒤 방향을 준다. |
| 노란 목도리 | 위에서 봤을 때 가장 크게 보이는 색 포인트. **나중에 팀 구분색으로 쓸 자리다.** |
| 어깨 망토깃(등 쪽으로 치우침) | 원래 등에 세로 망토를 달았더니 이 카메라에선 옆면이라 전혀 안 보였다. 어깨 위에 얹는 가로 판으로 바꿔서 위에서 등 방향이 읽히게 했다. |
| 튀어나온 눈 두 개 | 카멜레온풍. 멀리서도 어디를 보는지 읽힌다. |
| 마법봉: 오른손 위, 위로 32° + 바깥으로 12° | 카메라가 -32°로 내려다보므로 봉을 그만큼 젖혀야 화면에서 "앞으로 겨눈" 걸로 읽힌다. 안 젖히면 **땅을 가리키는 것처럼** 보인다(실제로 렌더해서 확인함). 바깥으로 12° 더 벌린 건 뒤에서 봤을 때 봉이 몸에 완전히 가려졌기 때문. |
| 마법봉 끝(발광 구, emission 3.2) | 이 캐릭터에서 유일하게 빛나는 부분. 투사체가 어디서 태어나는지 눈으로 알려준다. |

**색**: 몸 파랑 2톤 + 목도리 노랑, 끝. 채도를 더 늘리지 않았다.
스킬 투사체는 유저가 **아무 색이나** 고르므로 캐릭터가 색을 많이 먹으면 이펙트가 안 읽힌다.

**건드리지 않은 것**: `CollisionShape3D`(캡슐 r0.35 h1.7), `CamPivot / SpringArm3D / Camera3D`,
`Body`, `Body/Wand/Muzzle` 경로. 전부 `Player.gd` 가 참조한다.

### 2. 아레나 (`game/scenes/Arena.tscn`)

**의미 없는 상자 3개 → 가구가 찬 원룸 한 칸.**
방 60m ÷ 캐릭터 1.7m ≒ 실제 6m 방 안에 키 17cm 사람이 있는 비율. 벽도 12m → 18m 로 올렸다.

가구와 전투 의도:

| 가구 | 위치 | 높이 | 전투에서 하는 일 |
|---|---|---|---|
| 침대(프레임+매트리스+베개+이불) | 북서 | 매트 윗면 3.8m | 큰 덩어리. 정면 돌파 불가, 돌아가야 한다. 위는 고지대 |
| 책 3권 더미 | 침대 남동쪽 | 1.1m×3칸 | **유일한 고지대 진입로.** 점프 높이(1.2m) 안쪽이라 걸어 올라가진다 → 매트리스로 0.5m |
| 책상(상판+다리 4개) | 동/북동 | 상판 밑 7m | 다리 사이가 통로, 상판이 지붕. 밑에 들어가면 위쪽 시야가 끊긴다 |
| 의자(앉는 판+다리 4개+등받이) | 동 | 등받이 18m | 등받이가 남북 시야를 자르는 벽. 앉는 판 밑은 통로 |
| 머그컵(+손잡이) | 서 | 5m | 둥근 기둥 엄폐. 돌면서 싸우는 자리. **이 맵에서 색이 가장 센 물건** |
| 방석 2개 | 남서·동 | 1.1m | 낮은 엄폐. 뛰어 올라갈 수 있다 |
| 택배상자(대·소) | 남동 | 8m / 3.5m | 코너 채우기 |
| 연필(+심+지우개) | 남서 | 1.8m | 낮은 엄폐 + 스케일(작은 사람/큰 물건)을 설명하는 소품 |
| 창문(유리+창틀+창살) | **서쪽 벽** | — | 이 방의 광원. 판정 없음 |
| 문(문짝+문틀+손잡이) | 동쪽 벽 | — | "방"이라는 걸 알려주는 표식. 판정 없음 |
| 걸레받이 4면 | 벽 밑 | — | 고정 카메라에서 바닥/벽 경계를 읽게 하는 선 |

가운데(러그 위)는 **비워 뒀다.** 허수아비 3개와 플레이어 스폰이 거기 있고, 교전이 열려야 한다.

**창문을 서쪽에 둔 이유(중요)**: 카메라 yaw 가 0°로 고정이라 **북쪽 벽은 언제나 배경**이다.
거기에 밝은 창을 두면 밝은 면이 늘 화면 뒤에 깔려 투사체를 잡아먹는다.
그래서 북쪽 벽은 무늬 없는 차분한 회색으로 두고, 창은 옆(서쪽)에 뒀다.

`Floor`/`Walls` 의 `collision_layer=1`, `Dummies` 노드, `Player` 인스턴스는 그대로다.
`CollisionShape3D` 는 `StaticBody3D`의 직계 자식이어야 등록되므로 `Props` 밑을 평평하게 나열했다.
판정이 필요 없는 것(러그·창문·문·걸레받이·컵 손잡이·상자 뚜껑)은 별도 `Decor` 노드로 뺐다.

### 3. 색·조명 판단

**결론: 배경은 채도를 죽인 중간 톤으로 간다.** 스킬 투사체 색은 유저가 정하므로
배경이 특정 색을 먹으면 어떤 스킬은 보이고 어떤 스킬은 안 보이는 사태가 난다.

- 마루 = 밝은 따뜻한 나무(0.44,0.38,0.31) / 러그 = 중간 톤 중성 회색(0.42,0.41,0.42)
  → **색상은 다르고 명도는 가까운** 조합. 밝은 색이면 뭐가 날아와도 그 위에서 튄다.
- 벽 = 마루보다 밝은 회색 → 캐릭터(파랑, 중간~어두움)가 벽 앞에서 실루엣으로 뜬다.
- 색을 준 건 딱 몇 개: 머그컵(빨강), 책(초록/자주/남색), 이불(청록).
  `"빨간 컵 쪽으로 돌아가"` 같은 **위치 지시어**가 되라고 넣은 것이다.
- 조명: 서쪽 창에서 들어오는 햇빛(그림자 O, 0.7) + 반대편 약한 채움광(그림자 X, 0.12)
  + 천장 조명(0.55) + 앰비언트 0.7. 필모식 톤매핑.
- 글로우는 켰지만 문턱 1.3 / 강도 0.3 으로 **마법 이펙트만** 번지게 눌렀다.

렌더해서 확인하며 3번 다시 잡았다. 실패한 조합을 남겨 둔다(다시 밟지 말 것):
1. 앰비언트 0.8 + 글로우 문턱 1.0 → 화면 전체가 뿌옇게 떠서 실루엣이 사라졌다.
2. 앰비언트 0.42 → 벽은 하얗게 날고 바닥은 새까맣게 죽는 극단 대비가 됐다.
3. 러그를 진한 청색으로 → 화면 절반이 **어두운 호수**가 돼서 아무것도 안 읽혔다.

### 5. 개발/QA 에게 넘길 것

1. **`Muzzle` 위치가 바뀌었다.** Body 기준 대략 `(0.50, 1.38, -0.90)` (이전 `(0.3, 1.0, -1.15)`).

   `Player.gd` 는 Muzzle 의 **위치만** 쓰고 방향은 `Body` 의 -Z 를 쓰므로 조준은 안 틀어진다.
   다만 QA 는 두 가지를 봐 달라:
   - 허수아비 캡슐(0~1.8m)에 y=1.38 로 나가는 투사체가 정상적으로 맞는지
   - 오른쪽 벽에 붙어서 쏠 때 투사체가 벽 안에서 태어나지 않는지
2. **마법봉 끝 색을 스킬 색으로 물들이면 좋겠다.** 지금은 고정 주황(`mat_wand_tip`).
   `Player.gd` 가 `skill_color` 를 알고 있으니 `_reload_skill()` 에서
   `$Body/Wand/Tip` 재질의 `albedo/emission` 을 갈아끼우면 "지금 든 스킬"이 손에서 보인다.
   아트 쪽 준비는 끝났다(Tip 이 독립 MeshInstance3D, 재질도 독립).
3. **엄폐물 높이 기준선**: 점프 높이가 `jump_height = 1.2` 라서
   **1.1m 이하 = 올라갈 수 있음 / 1.4m 이상 = 못 올라감** 으로 잡고 배치했다.
   밸런스가 점프 높이를 바꾸면 방석(1.1m)과 책 계단(1.1m×3)이 같이 흔들린다. 알려 달라.
4. **카메라가 가구에 닿으면 SpringArm 이 당겨진다.** 책상 상판 밑(7m)은 카메라(약 5.2m)가
   들어가도록 일부러 높게 잡았지만, 의자 등받이(18m) 옆을 지날 땐 카메라가 확 당겨진다.
   플레이해 보고 불편하면 등받이 높이를 낮추면 된다(아트 쪽에서 조정 가능).

### 0. ⚠ 먼저 — 이 프로젝트 전체에 걸린 오독을 하나 잡았다

**`.tscn` 의 `Transform3D(a0…a8, ox,oy,oz)` 12개 숫자는 basis 를 「행(row)」 순서로 적는다.**

```
실제 축(열벡터):  X축 = (a0, a3, a6)   Y축 = (a1, a4, a7)   Z축 = (a2, a5, a8)
```

`(a0,a1,a2)` 를 X축으로 읽으면 **전치 행렬**이 되어 회전이 반대로 간다.
지난 세션(나)의 리포트에 있는 두 문장이 이 오독의 결과다:

| 종전 기록 | 실제 |
|---|---|
| 「Muzzle 은 Body 기준 대략 **(0.50, 1.38, -0.90)**」 | **(0.2652, 0.7492, -0.8974)** — 허리 높이다 |
| 「마법봉을 **위로 32°** 들어올렸다」 | 실제로는 **앞아래 약 27°** 를 향한다 |

화면에서 봉 끝이 머리 옆에 보이는 것은, 봉 끝이 **0.78m 앞에** 있어서 -32° 카메라에서
머리와 같은 화면 높이로 투영되기 때문이다. 렌더 픽셀 좌표를 직접 재서 확인했다
(예측 오차: 행 기준 24px vs 실측 24px / 열 기준이면 30px 위로 떠야 한다).

- **QA 에게**: 지난 리포트의 「Muzzle 이 y=1.38 로 올라갔으니 허수아비 상단 판정을 봐 달라」는
  요청은 **전제가 틀렸다.** 총구는 y≈0.75 다. 허수아비 캡슐(0~1.8m) 한가운데라 오히려 안전하다.
- **개발에게**: `.tscn` 을 손으로 쓸 때 basis 를 열 기준으로 적으면 회전이 조용히 반대로 간다.
  이번에도 화살촉을 그렇게 적어서 **촉이 카메라 쪽을 향한 채로 렌더**됐고, 렌더로 잡았다.

### 1. 🔴 발이 배경에 박히는 버그 — 원인은 캐릭터가 아니라 **러그**였다

**렌더 확인(수정 전)**: 스폰 지점에서 **신발이 화면에 아예 안 보였다.**
종아리가 러그 면에서 칼로 자른 듯 잘려 있었다. 사용자가 본 그대로다.

**원인 (숫자로)**

| 것 | 값 |
|---|---|
| `CollisionShape3D` 캡슐 바닥 | y = **0.0** → 캐릭터는 y=0 에 선다 |
| 신발(`mesh_foot` 0.09 높이 @ y=0.05) 밑창 | y = **0.005** |
| `Decor/Rug` 윗면 (판정 없음) | y = **0.12** |
| `Decor/RugInner` 윗면 (판정 없음) | y = **0.19** |

러그는 `Decor` 라 **판정이 없다.** 그래서 캐릭터는 러그를 안 밟고 바닥에 서는데,
러그 표면은 신발 꼭대기(0.095)보다도 높다 → **발 전체 + 종아리 아래가 잠긴다.**
스폰 좌표 `(0, 0.1, 12)` 가 바깥 러그 위라서 게임을 켜자마자 보이는 상태였다.

**조치 (`CollisionShape3D` 는 안 건드렸다)**

| 대상 | 종전 | 개정 |
|---|---|---|
| `Decor/Rug` 위치 y | 0.06 (윗면 0.12) | **-0.056** (윗면 **0.004**) |
| `Decor/RugInner` 위치 y | 0.13 (윗면 0.19) | **-0.052** (윗면 **0.008**) |
| `FootL/FootR` 밑창 | 0.005 | **0.015** |

- 러그를 바닥 박스 속으로 밀어 넣어 **윗면만 4~8mm 남겼다.** 옆면은 바닥에 묻혀 안 보이므로
  화면에는 그냥 "바닥에 깔린 평평한 러그"로 읽힌다(렌더 확인 — 러그 모양 그대로 남아 있다).
- 0 이 아니라 4mm 를 띄운 이유: 바닥 윗면과 **같은 평면이면 Z-파이팅**이 난다.
  7m 거리에서 깊이 분해능은 0.1mm 미만이라 4mm 면 충분히 안전하다.
- 신발이 맨바닥 위에서 **15mm 뜬다.** -32° 부감에서는 신발의 윗면을 보므로 그 틈이 안 보인다
  (7m 거리에서 2px, 게다가 그림자가 덮는다). **박히는 것보다 뜨는 쪽이 압도적으로 덜 보인다** —
  판정면(y=0)을 못 옮기는 이상 이게 최선의 절충이다.
- ⚠ **러그에 판정을 주는 방법은 일부러 안 썼다.** 아레나 한가운데에 12cm 단차가 생기면
  점프 높이 1.2m / 엄폐 1.1m 기준에 없던 변수가 끼어든다.

**덤으로 고친 것 — 걸레받이(`Decor/Trim*`)**: 두께 0.4 → **0.06**, 위치 ±29.3 → **±29.47**.
벽 판정면은 |29.5| 인데 걸레받이가 0.4 나 튀어나와 있어 **벽에 붙어 서면 캐릭터가 걸레받이 안에
박혀 보였다.** 화면에서 읽히는 건 두께가 아니라 세로면(높이 1.8)이라 얇게 해도 선은 그대로다.

### 2. 🔴 개발이 쓸 노드 경로 계약 — **관절 피벗**

종전에는 메시가 전부 `Body` 밑에 평평하게 놓여 있었다. 그 상태로 다리를 돌리면
**엉덩이가 아니라 다리 한가운데를 축으로** 돌아 다리가 몸에서 빠져나간다.
움직여야 할 관절마다 **basis 가 단위행렬인 빈 `Node3D`** 를 관절 위치에 두고 메시를 매달았다.

#### 계약 표 — 이 경로와 부호는 아트가 보증한다

| 피벗 경로 | Body 기준 위치 | 밑에 달린 것 | 주 회전축 |
|---|---|---|---|
| `$Body/Neck` | (0, 1.14, 0) | 머리·모자·눈·눈동자 | x (끄덕), y (좌우 보기) |
| `$Body/ShoulderL` | (-0.27, 1.06, 0) | ArmL, HandL | **x** (앞뒤 흔들기) |
| **`$Body/Wand`** ★ | ( 0.27, 1.06, 0) | ArmR, HandR, Rod(마법봉), Muzzle | **x** (팔 들어올리기) |
| `$Body/Wand/Rod` | (0.12, 0, -0.4) | Stick, Tip | x (손목 스냅) |
| `$Body/HipL` | (-0.115, 0.53, 0) | LegL, AnkleL, FootL | **x** (다리 차기), z (벌리기) |
| `$Body/HipL/AnkleL` | (0, -0.46, 0) | FootL | **x** (발끝 들기) |
| `$Body/HipR` | ( 0.115, 0.53, 0) | LegR, AnkleR, FootR | 〃 |
| `$Body/HipR/AnkleR` | (0, -0.46, 0) | FootR | 〃 |
| `$Body/AimArrow` | (0, 0.03, 0) | RailL, RailR, Point | (회전 안 함 — 아래 3절) |

**★ `Body/Wand` 를 오른쪽 어깨 피벗으로 겸용한 이유 — 여기가 제일 중요하다.**
`Player.gd` 가 `$Body/Wand/Muzzle` 을 참조한다. 어깨 피벗을 새로 끼워 넣으면 그 경로가 깨진다.
그래서 **Wand 노드 자체를 어깨 관절 위치로 옮기고** 오른팔·오른손·마법봉을 그 밑에 넣었다.
- **경로 `$Body/Wand/Muzzle` 은 그대로다. 개발이 고칠 코드가 없다.**
- **Muzzle 의 최종 위치도 한 자리도 안 바뀐다** (Body 기준 `(0.2652, 0.7492, -0.8974)`).
- 덕분에 **`$Body/Wand.rotation.x` 한 줄로 팔+손+마법봉이 통째로** 올라간다 —
  사용자가 콕 집어 요구한 「팔을 위로 올렸다가 내리는 모션」이 이 값 하나로 나온다.
- 이름이 실제 역할(어깨)과 다른 건 인정한다. **개명 금지 규칙이 우선이라 그렇게 했다.**

#### 회전 부호 규칙 (전 관절 공통, 단위행렬 basis 라 섞을 일 없다)

```
rotation.x 양수 → 매달린 것이 앞(-Z)쪽으로 돈다.  다리는 앞으로 차고, 팔은 앞→위로 올라간다.
rotation.z 양수 → +X(캐릭터 오른쪽)으로 벌어진다.
rotation.y 양수 → 위에서 봤을 때 반시계.
```

#### ⛔ 쓰면 안 되는 것 / 대체 수단

- `$Body.rotation.x` — `_tick_flip()` 이 덤블링에 쓰고 매 프레임 0 으로 되돌린다. **애니메이션에 못 쓴다.**
- `$Body.rotation.y` — `_face()` 가 쓴다. 못 쓴다.
- **상하 바운스/스쿼시는 `$Body.position.y` 로 해라.** 코드가 안 건드리는 자리다.
- **가슴(chest) 피벗은 못 만들었다.** 만들면 `Body/Wand` 가 Body 의 직계 자식이 아니게 돼
  `$Body/Wand/Muzzle` 이 깨진다. 상체 기울임이 꼭 필요하면 `Neck` + 양 어깨를 같이 돌려라.
- 덤블링이 **발밑(y=0)을 축으로** 돈다. 몸 가운데(y≈0.85)를 축으로 돌리고 싶으면
  Body 를 돌리면서 `position.y` 로 보정해야 한다. 같은 이유로 아트가 노드를 못 끼워 준다.

#### 아트가 제안하는 수치 (그대로 써도 되고 조정해도 된다)

**걷기** — `move_speed 6.0`, 보폭 ≈ 0.62m → 다리 한 주기 ≈ 0.84초.
`phase += (수평속도 / 0.62) * TAU * delta` 로 위상을 굴리면 속도에 맞춰 자동으로 빨라진다.

| 노드 | 값 |
|---|---|
| `HipL.rotation.x` | `deg_to_rad(26) * sin(phase)` |
| `HipR.rotation.x` | 위상 +π (반대 다리) |
| `AnkleL/R.rotation.x` | `deg_to_rad(12) * sin(phase - 0.7)` (착지 직전 발끝 들림) |
| `ShoulderL.rotation.x` | `deg_to_rad(20) * sin(phase + π)` (다리와 대각) |
| `Wand.rotation.x` | `deg_to_rad(7) * sin(phase)` — **마법봉을 들었으니 오른팔은 작게** |
| `Body.position.y` | `0.045 * abs(sin(phase))` (두 걸음에 두 번 튄다) |
| `Neck.rotation.x` | `deg_to_rad(3) * sin(phase * 2)` |

**점프/공중**: `HipL/R.x = -14°`(다리 뒤로 모음), `AnkleL/R.x = +18°`, `ShoulderL.x = -40°`(팔 위로),
`Wand.x = +25°`. 착지 순간 `Body.position.y` 를 -0.09 → 0 으로 0.12초 스쿼시.

**스킬 시전** (`cast_time` 0.28~1.10초, `t` = 0→1 진행률) — 사용자가 요구한 모션:

| 구간 | 동작 |
|---|---|
| t 0 → 0.55 | `Wand.rotation.x` **0° → +72°** (팔+마법봉 위로 번쩍) · `ShoulderL.x -25°` · `Neck.x +6°` |
| t 0.55 → 0.78 | **정지(anticipation hold)** — 여기서 멈춰야 다음 동작이 세게 보인다 |
| t 0.78 → 1.0 | `Wand.rotation.x` **+72° → -18°** (내리치기, 오버슛) · `Rod.rotation.x` 를 **반대로** -20°→+10° 얹으면 손목 스냅이 생긴다 |
| 발사 후 0.14초 | `Wand.rotation.x` -18° → 0° 복귀 |

`ease_out_cubic` 으로 올리고 `ease_in_quart` 로 내리쳐라. **올릴 때 느리고 내릴 때 빠르면** 「탁」 하고 꽂힌다.
`cast_time` 이 짧은 스킬(0.28초)은 위 비율을 그대로 압축하면 된다 — 정지 구간이 짧아도 리듬은 남는다.

### 3. 조준 방향 표시 — `$Body/AimArrow`

사용자 요구: 「스킬이 날아가는 방향을 화살표나 이런 걸로 보이게」.

#### 노드 경로

```
$Body/AimArrow            Node3D          (0, 0.03, 0)
  ├ $Body/AimArrow/RailL  MeshInstance3D  왼쪽 레일 (BoxMesh 0.13 x 0.02 x 2.269, -7.5도)
  ├ $Body/AimArrow/RailR  MeshInstance3D  오른쪽 레일
  └ $Body/AimArrow/Point  MeshInstance3D  화살촉 (PrismMesh 1.05 x 1.4, 꼭짓각 41도)
```

**개발이 코드로 할 것**: 켜고 끄기(`$Body/AimArrow.visible`) · 시전 중 강조 · 덤블링 중 끄기.
**방향 회전은 코드가 필요 없다** — `Body` 밑에 달아서 `_face()` 가 Body 를 돌리면 저절로 따라 돈다.
즉 이 화살표는 언제나 `Player.aim_direction()` 과 **정확히** 같은 방향을 가리킨다.
⚠ 단, `_tick_flip()` 이 덤블링 때 `Body.rotation.x` 를 돌리므로 **그때는 화살표도 같이 돈다.**
`if _flip_left > 0.0: $Body/AimArrow.visible = false` 한 줄만 넣어 달라.

#### 왜 「가운데 한 줄 화살표」가 아니라 「레일 두 줄 + 떨어진 촉」인가

**카메라가 -32° 고정이라 북쪽(-Z)을 보면 바닥 화살표가 캐릭터 몸에 통째로 가린다.**
실제로 화면 세로 각도를 계산했다(카메라는 플레이어 기준 (0, 5.21, 5.94), 정면 -32°):

| 대상 | 화면 세로각 |
|---|---|
| 캐릭터 발밑 | -9.17° |
| **모자 꼭대기** | **+2.00°** |
| 바닥에 누운 2.9m 화살표 끝 | +1.63° ← **모자보다 낮다 = 완전히 가려진다** |

그래서 세 가지를 했고, 셋 다 렌더로 검증했다:

1. **레일을 몸통 바깥(±0.78m)으로 뺐다.** 캐릭터 실루엣 밖이라 어느 방향에서도 안 가린다.
2. **레일을 앞으로 7.5° 모았다.** 평행 두 줄은 「골대」로 읽혔다 — 모아야 방향이 생긴다.
3. **화살촉을 4.5m 앞에 뒀다**(화면 +5.6°, 모자보다 3.6° 위). 머리 위로 확실히 넘어간다.

**시행착오 기록 (다시 밟지 말 것)**
- 촉을 폭 1.72 / 길이 0.95(꼭짓각 84°)로 잡았더니 **화살이 아니라 지붕**으로 읽혔다.
  → 1.05 × 1.4(꼭짓각 41°)로 좁고 길게.
- 촉을 3.3~4.0m 로 당겼더니 모자에 붙어 **천막(정자)** 으로 읽혔다. → 4.5m.
- 레일 끝과 촉 밑변을 붙였더니 바깥선이 한 줄로 이어져 또 천막이 됐다.
  → **0.5m 를 일부러 띄웠다.** 이 틈이 「레일 / 촉」을 두 물체로 갈라 준다.

**⚠ 알려진 손해**: **정남향(카메라 쪽)일 때 화살촉이 화면 아래 스킬바 뒤로 빠진다.**
바닥 지시자를 카메라 쪽으로 눕히면 원근이 커져서 생기는 구조적 문제고,
북쪽 가독성(4.5m 이상 필요)과 남쪽 가독성(3.7m 이하 필요)이 **정면충돌**한다.
남쪽은 캐릭터 얼굴과 마법봉이 정면으로 보여 방향이 이미 자명하므로 **북쪽을 우선**했다.
신경 쓰이면 개발이 `$Body/AimArrow.scale.z` 를 0.55~1.0 으로 줄이면 된다(카메라 쪽을 볼수록 짧게).

#### 색 — 왜 「차가운 흰색」인가

- `mat_aim_rail` : unshaded · `Color(0.78, 0.88, 1.0, 0.30)`
- `mat_aim_head` : unshaded · `Color(0.88, 0.94, 1.0, 0.50)`

1. **투사체 색은 유저가 아무 색이나 고른다.** 특정 색상(hue)을 쓰면 그 색 스킬을 쓸 때
   조준선과 투사체가 서로를 잡아먹는다. **흰색은 상대 색이 없다.**
2. 바닥(0.44,0.38,0.31 따뜻한 나무)·러그(0.42 회색)와는 **명도**로 갈린다.
   살짝 푸른 기를 넣어 따뜻한 바닥 위에서 "물체"가 아니라 "빛"으로 읽히게 했다.
3. **`shading_mode = unshaded`** — 그림자(책상 밑·침대 옆)에 들어가도 밝기가 안 변한다.
   조준선이 어두운 데서 사라지면 쓸모가 없다.
4. **`emission` 을 안 썼다.** 글로우 문턱(1.3)을 넘기면 조준선이 번져서
   **마법 이펙트 전용으로 남겨 둔 글로우**를 조준선이 나눠 갖는다.

**개발에게 추천(선택)**: 재질이 `surface_material_override` 로 노드마다 독립이므로
시전 중에 `Point` 의 albedo 를 **그 슬롯의 skill_color** 로 갈아끼우면
「지금 이 색 스킬이 이쪽으로 나간다」가 한 번에 읽힌다. 알파는 0.5 유지 권장.

### 4. 킬 임팩트 연출 제안 — 「쿵」의 설계

화면 흔들림은 개발이 코드로 넣는다. 아트가 정하는 것은 **얼마나 · 어떤 곡선 · 무엇을 더 얹느냐**다.

#### 세기의 기준선 먼저

카메라 거리 7m, 세로 FOV 70° → 화면에 보이는 세로 높이 **9.80m**.
즉 카메라를 **0.10m 옮기면 화면 높이의 1.02%** 다. 이걸 자로 쓴다.

- 1% 미만 → 안 보인다. 넣으나 마나.
- **1.5 ~ 3%** → 「쿵」. 여기가 정답 구간.
- 4% 이상 또는 0.6초 이상 → **멀미.** 이 게임은 카메라가 고정각이라
  플레이어가 시점으로 보정할 수단이 없다. 다른 게임보다 상한이 낮다.

#### 흔들림 스펙 (총 0.35초)

| 요소 | 값 |
|---|---|
| 흔들 대상 | **`$CamPivot/SpringArm3D/Camera3D.position`** (로컬 x/y). SpringArm 의 벽 충돌 보정을 안 건드린다 |
| ① 방향 펀치 | 피격자 방향(화면 투영)으로 **0.20m**(2.0%). 0.045초 `ease_out` 으로 나갔다가 0.11초 `ease_out_back`(살짝 오버슛)으로 복귀 |
| ② 노이즈 떨림 | 진폭 **0.10m**, **22Hz**, `A × (1-t)^2.2` 감쇠, **0.28초**. 서로 나눠떨어지지 않는 두 주파수(예: 22Hz·31Hz)를 섞어야 주기적으로 안 보인다 |
| ③ FOV 킥 | `70 → 73.5` 를 0.05초, `→ 70` 을 0.20초 `ease_out`. **「쿵」을 실제로 파는 건 이거다** — 세상이 앞으로 확 다가온다 |
| ⛔ 회전(roll) | **넣지 마라.** 「화면 위쪽이 언제나 북쪽」이 이 게임 카메라 설계의 전제다. 롤은 그걸 깬다 |
| 다중 킬 | trauma 를 1.0 으로 **clamp**. 0.15초 안에 두 명 죽어도 두 배로 안 흔들린다 |

곡선은 Squirrel Eiserloh 식으로: `trauma` 를 저장하고 **흔들림 ∝ trauma²**,
`trauma -= 3.5 * delta`. 제곱이라 끝이 부드럽게 죽어서 「멈추다 만」 느낌이 안 난다.

#### 흔들림 말고 더 얹을 것 — 우선순위 순

1. **히트스톱 (제일 중요, 제일 쌈)** — `Engine.time_scale = 0.05` 를 **0.07초**.
   흔들림이 **재생 재개 순간에 터지도록** 배치하면 체감이 두 배가 된다.
   ⚠ 반드시 실시간 기준으로 풀어야 한다(`process_mode = ALWAYS` 타이머 또는 스케일 안 걸린 delta).
   안 그러면 시간이 안 돌아온다.
2. **피격자 백색 섬광** — **전체화면 플래시는 넣지 마라**(고정 카메라에서 너무 폭력적이다).
   대신 죽는 대상의 재질 `emission` 을 **백색 energy 6.0** 으로 0.06초.
   글로우 문턱(1.3)을 넘으므로 **여기서 블룸이 터진다.** 글로우를 마법용으로 아껴 둔 이유가 이것이다.
3. **바닥 충격파 링** — 죽은 자리 발밑에 납작한 링(토러스 또는 스케일한 판) 하나.
   지름 **0 → 3.0m 를 0.30초**, 알파 0.9 → 0, 두께도 같이 얇아짐.
   **-32° 부감은 바닥 링을 가장 예쁘게 보여주는 각도다.** 이 카메라가 공짜로 주는 연출이니 꼭 써라.
4. **파편** — 시체를 **8~12개 박스**로 터뜨린다. 위쪽으로 치우친 랜덤 임펄스 3~6m/s + 회전,
   0.9초에 걸쳐 축소·페이드. 조각 크기 0.2~0.4m 가 이 맵 스케일에서 잘 읽힌다.
5. **비네트 펄스**(선택) — 화면 가장자리를 0.25초간 12% 어둡게. 시선을 가운데로 모은다.
   **화면 전체 색조 변경은 하지 마라** — 투사체 색이 유저 마음대로라 어떤 색은 묻힌다.
