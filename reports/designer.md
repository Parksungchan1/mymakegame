# 디자인 담당 진행 기록

## 2026-07-31 — 캐릭터·아레나 1차 아트 (임시 도형 → 실제 디자인)

### 왜 했나
그때까지 화면에 있던 건 **흰 캡슐 + 검은 박스(얼굴)** 하나와 **회색 상자 3개가 놓인 빈 방**이었다.
전부 개발이 동작 확인용으로 세운 플레이스홀더였고, 기획서가 정한 그림과 아무 관계가 없었다.

기준으로 삼은 기획서 문장:
- 10행 「맵: **거대한 원룸 한 칸**, 소형 인간들이 싸움」
- 10행 「캐릭터/속도는 **멧챠 카멜레온풍**」 (작고 날쌘)
- 12행 「이펙트: **마법봉으로 마법 쓰는 연출**」
- 61~69행 ✅결정됨 「카메라 **고정 각도**」 (yaw 0°, pitch -32°, 7m)

고친 파일은 `game/scenes/Player.tscn`, `game/scenes/Arena.tscn` **둘뿐**이다.
스크립트·기획 문서·STATUS 는 건드리지 않았다.

### 1. 캐릭터 (`game/scenes/Player.tscn`)

**2등신 마법사.** 캡슐 하나 → 머리·몸통·팔·다리·발·모자·망토깃·눈·마법봉 구성.

| 부위 | 의도 |
|---|---|
| 머리 크게 / 몸통·팔다리 짧게 | 위에서 -32°로 내려다보는 화면에서는 머리가 화면의 대부분이다. 2등신이라야 "사람"으로 읽힌다. |
| 고깔모자(앞으로 10° 기울임) | 마법봉과 짝을 이루는 실루엣. 기울여서 앞뒤 방향을 준다. |
| 노란 목도리 | 위에서 봤을 때 가장 크게 보이는 색 포인트. **나중에 팀 구분색으로 쓸 자리다.** |
| 어깨 망토깃(등 쪽으로 치우침) | 원래 등에 세로 망토를 달았더니 이 카메라에선 옆면이라 전혀 안 보였다. 어깨 위에 얹는 가로 판으로 바꿔서 위에서 등 방향이 읽히게 했다. |
| 튀어나온 눈 두 개 | 카멜레온풍. 멀리서도 어디를 보는지 읽힌다. |
| 마법봉: 오른손 위, 위로 32° + 바깥으로 12° | 카메라가 -32°로 내려다보므로 봉을 그만큼 젖혀야 화면에서 "앞으로 겨눈" 걸로 읽힌다. 안 젖히면 **땅을 가리키는 것처럼** 보인다(실제로 렌더해서 확인함). 바깥으로 12° 더 벌린 건 뒤에서 봤을 때 봉이 몸에 완전히 가려졌기 때문. |
| 마법봉 끝(발광 구, emission 3.2) | 이 캐릭터에서 유일하게 빛나는 부분. 투사체가 어디서 태어나는지 눈으로 알려준다. |

**색**: 몸 파랑 2톤 + 목도리 노랑, 끝. 채도를 더 늘리지 않았다.
스킬 투사체는 유저가 **아무 색이나** 고르므로 캐릭터가 색을 많이 먹으면 이펙트가 안 읽힌다.

**건드리지 않은 것**: `CollisionShape3D`(캡슐 r0.35 h1.7), `CamPivot / SpringArm3D / Camera3D`,
`Body`, `Body/Wand/Muzzle` 경로. 전부 `Player.gd` 가 참조한다.

### 2. 아레나 (`game/scenes/Arena.tscn`)

**의미 없는 상자 3개 → 가구가 찬 원룸 한 칸.**
방 60m ÷ 캐릭터 1.7m ≒ 실제 6m 방 안에 키 17cm 사람이 있는 비율. 벽도 12m → 18m 로 올렸다.

가구와 전투 의도:

| 가구 | 위치 | 높이 | 전투에서 하는 일 |
|---|---|---|---|
| 침대(프레임+매트리스+베개+이불) | 북서 | 매트 윗면 3.8m | 큰 덩어리. 정면 돌파 불가, 돌아가야 한다. 위는 고지대 |
| 책 3권 더미 | 침대 남동쪽 | 1.1m×3칸 | **유일한 고지대 진입로.** 점프 높이(1.2m) 안쪽이라 걸어 올라가진다 → 매트리스로 0.5m |
| 책상(상판+다리 4개) | 동/북동 | 상판 밑 7m | 다리 사이가 통로, 상판이 지붕. 밑에 들어가면 위쪽 시야가 끊긴다 |
| 의자(앉는 판+다리 4개+등받이) | 동 | 등받이 18m | 등받이가 남북 시야를 자르는 벽. 앉는 판 밑은 통로 |
| 머그컵(+손잡이) | 서 | 5m | 둥근 기둥 엄폐. 돌면서 싸우는 자리. **이 맵에서 색이 가장 센 물건** |
| 방석 2개 | 남서·동 | 1.1m | 낮은 엄폐. 뛰어 올라갈 수 있다 |
| 택배상자(대·소) | 남동 | 8m / 3.5m | 코너 채우기 |
| 연필(+심+지우개) | 남서 | 1.8m | 낮은 엄폐 + 스케일(작은 사람/큰 물건)을 설명하는 소품 |
| 창문(유리+창틀+창살) | **서쪽 벽** | — | 이 방의 광원. 판정 없음 |
| 문(문짝+문틀+손잡이) | 동쪽 벽 | — | "방"이라는 걸 알려주는 표식. 판정 없음 |
| 걸레받이 4면 | 벽 밑 | — | 고정 카메라에서 바닥/벽 경계를 읽게 하는 선 |

가운데(러그 위)는 **비워 뒀다.** 허수아비 3개와 플레이어 스폰이 거기 있고, 교전이 열려야 한다.

**창문을 서쪽에 둔 이유(중요)**: 카메라 yaw 가 0°로 고정이라 **북쪽 벽은 언제나 배경**이다.
거기에 밝은 창을 두면 밝은 면이 늘 화면 뒤에 깔려 투사체를 잡아먹는다.
그래서 북쪽 벽은 무늬 없는 차분한 회색으로 두고, 창은 옆(서쪽)에 뒀다.

`Floor`/`Walls` 의 `collision_layer=1`, `Dummies` 노드, `Player` 인스턴스는 그대로다.
`CollisionShape3D` 는 `StaticBody3D`의 직계 자식이어야 등록되므로 `Props` 밑을 평평하게 나열했다.
판정이 필요 없는 것(러그·창문·문·걸레받이·컵 손잡이·상자 뚜껑)은 별도 `Decor` 노드로 뺐다.

### 3. 색·조명 판단

**결론: 배경은 채도를 죽인 중간 톤으로 간다.** 스킬 투사체 색은 유저가 정하므로
배경이 특정 색을 먹으면 어떤 스킬은 보이고 어떤 스킬은 안 보이는 사태가 난다.

- 마루 = 밝은 따뜻한 나무(0.44,0.38,0.31) / 러그 = 중간 톤 중성 회색(0.42,0.41,0.42)
  → **색상은 다르고 명도는 가까운** 조합. 밝은 색이면 뭐가 날아와도 그 위에서 튄다.
- 벽 = 마루보다 밝은 회색 → 캐릭터(파랑, 중간~어두움)가 벽 앞에서 실루엣으로 뜬다.
- 색을 준 건 딱 몇 개: 머그컵(빨강), 책(초록/자주/남색), 이불(청록).
  `"빨간 컵 쪽으로 돌아가"` 같은 **위치 지시어**가 되라고 넣은 것이다.
- 조명: 서쪽 창에서 들어오는 햇빛(그림자 O, 0.7) + 반대편 약한 채움광(그림자 X, 0.12)
  + 천장 조명(0.55) + 앰비언트 0.7. 필모식 톤매핑.
- 글로우는 켰지만 문턱 1.3 / 강도 0.3 으로 **마법 이펙트만** 번지게 눌렀다.

렌더해서 확인하며 3번 다시 잡았다. 실패한 조합을 남겨 둔다(다시 밟지 말 것):
1. 앰비언트 0.8 + 글로우 문턱 1.0 → 화면 전체가 뿌옇게 떠서 실루엣이 사라졌다.
2. 앰비언트 0.42 → 벽은 하얗게 날고 바닥은 새까맣게 죽는 극단 대비가 됐다.
3. 러그를 진한 청색으로 → 화면 절반이 **어두운 호수**가 돼서 아무것도 안 읽혔다.

1. **`Muzzle` 위치가 바뀌었다.** Body 기준 대략 `(0.50, 1.38, -0.90)` (이전 `(0.3, 1.0, -1.15)`).

   `Player.gd` 는 Muzzle 의 **위치만** 쓰고 방향은 `Body` 의 -Z 를 쓰므로 조준은 안 틀어진다.
   다만 QA 는 두 가지를 봐 달라:
   - 허수아비 캡슐(0~1.8m)에 y=1.38 로 나가는 투사체가 정상적으로 맞는지
   - 오른쪽 벽에 붙어서 쏠 때 투사체가 벽 안에서 태어나지 않는지
2. **마법봉 끝 색을 스킬 색으로 물들이면 좋겠다.** 지금은 고정 주황(`mat_wand_tip`).
   `Player.gd` 가 `skill_color` 를 알고 있으니 `_reload_skill()` 에서
   `$Body/Wand/Tip` 재질의 `albedo/emission` 을 갈아끼우면 "지금 든 스킬"이 손에서 보인다.
   아트 쪽 준비는 끝났다(Tip 이 독립 MeshInstance3D, 재질도 독립).
3. **엄폐물 높이 기준선**: 점프 높이가 `jump_height = 1.2` 라서
   **1.1m 이하 = 올라갈 수 있음 / 1.4m 이상 = 못 올라감** 으로 잡고 배치했다.
   밸런스가 점프 높이를 바꾸면 방석(1.1m)과 책 계단(1.1m×3)이 같이 흔들린다. 알려 달라.
4. **카메라가 가구에 닿으면 SpringArm 이 당겨진다.** 책상 상판 밑(7m)은 카메라(약 5.2m)가
   들어가도록 일부러 높게 잡았지만, 의자 등받이(18m) 옆을 지날 땐 카메라가 확 당겨진다.
   플레이해 보고 불편하면 등받이 높이를 낮추면 된다(아트 쪽에서 조정 가능).

### 0. ⚠ 먼저 — 이 프로젝트 전체에 걸린 오독을 하나 잡았다

**`.tscn` 의 `Transform3D(a0…a8, ox,oy,oz)` 12개 숫자는 basis 를 「행(row)」 순서로 적는다.**

```
실제 축(열벡터):  X축 = (a0, a3, a6)   Y축 = (a1, a4, a7)   Z축 = (a2, a5, a8)
```

`(a0,a1,a2)` 를 X축으로 읽으면 **전치 행렬**이 되어 회전이 반대로 간다.
지난 세션(나)의 리포트에 있는 두 문장이 이 오독의 결과다:

| 종전 기록 | 실제 |
|---|---|
| 「Muzzle 은 Body 기준 대략 **(0.50, 1.38, -0.90)**」 | **(0.2652, 0.7492, -0.8974)** — 허리 높이다 |
| 「마법봉을 **위로 32°** 들어올렸다」 | 실제로는 **앞아래 약 27°** 를 향한다 |

화면에서 봉 끝이 머리 옆에 보이는 것은, 봉 끝이 **0.78m 앞에** 있어서 -32° 카메라에서
머리와 같은 화면 높이로 투영되기 때문이다. 렌더 픽셀 좌표를 직접 재서 확인했다
(예측 오차: 행 기준 24px vs 실측 24px / 열 기준이면 30px 위로 떠야 한다).

- **QA 에게**: 지난 리포트의 「Muzzle 이 y=1.38 로 올라갔으니 허수아비 상단 판정을 봐 달라」는
  요청은 **전제가 틀렸다.** 총구는 y≈0.75 다. 허수아비 캡슐(0~1.8m) 한가운데라 오히려 안전하다.
- **개발에게**: `.tscn` 을 손으로 쓸 때 basis 를 열 기준으로 적으면 회전이 조용히 반대로 간다.
  이번에도 화살촉을 그렇게 적어서 **촉이 카메라 쪽을 향한 채로 렌더**됐고, 렌더로 잡았다.

### 1. 🔴 발이 배경에 박히는 버그 — 원인은 캐릭터가 아니라 **러그**였다

**렌더 확인(수정 전)**: 스폰 지점에서 **신발이 화면에 아예 안 보였다.**
종아리가 러그 면에서 칼로 자른 듯 잘려 있었다. 사용자가 본 그대로다.

**원인 (숫자로)**

| 것 | 값 |
|---|---|
| `CollisionShape3D` 캡슐 바닥 | y = **0.0** → 캐릭터는 y=0 에 선다 |
| 신발(`mesh_foot` 0.09 높이 @ y=0.05) 밑창 | y = **0.005** |
| `Decor/Rug` 윗면 (판정 없음) | y = **0.12** |
| `Decor/RugInner` 윗면 (판정 없음) | y = **0.19** |

러그는 `Decor` 라 **판정이 없다.** 그래서 캐릭터는 러그를 안 밟고 바닥에 서는데,
러그 표면은 신발 꼭대기(0.095)보다도 높다 → **발 전체 + 종아리 아래가 잠긴다.**
스폰 좌표 `(0, 0.1, 12)` 가 바깥 러그 위라서 게임을 켜자마자 보이는 상태였다.

**조치 (`CollisionShape3D` 는 안 건드렸다)**

| 대상 | 종전 | 개정 |
|---|---|---|
| `Decor/Rug` 위치 y | 0.06 (윗면 0.12) | **-0.056** (윗면 **0.004**) |
| `Decor/RugInner` 위치 y | 0.13 (윗면 0.19) | **-0.052** (윗면 **0.008**) |
| `FootL/FootR` 밑창 | 0.005 | **0.015** |

- 러그를 바닥 박스 속으로 밀어 넣어 **윗면만 4~8mm 남겼다.** 옆면은 바닥에 묻혀 안 보이므로
  화면에는 그냥 "바닥에 깔린 평평한 러그"로 읽힌다(렌더 확인 — 러그 모양 그대로 남아 있다).
- 0 이 아니라 4mm 를 띄운 이유: 바닥 윗면과 **같은 평면이면 Z-파이팅**이 난다.
  7m 거리에서 깊이 분해능은 0.1mm 미만이라 4mm 면 충분히 안전하다.
- 신발이 맨바닥 위에서 **15mm 뜬다.** -32° 부감에서는 신발의 윗면을 보므로 그 틈이 안 보인다
  (7m 거리에서 2px, 게다가 그림자가 덮는다). **박히는 것보다 뜨는 쪽이 압도적으로 덜 보인다** —
  판정면(y=0)을 못 옮기는 이상 이게 최선의 절충이다.
- ⚠ **러그에 판정을 주는 방법은 일부러 안 썼다.** 아레나 한가운데에 12cm 단차가 생기면
  점프 높이 1.2m / 엄폐 1.1m 기준에 없던 변수가 끼어든다.

**덤으로 고친 것 — 걸레받이(`Decor/Trim*`)**: 두께 0.4 → **0.06**, 위치 ±29.3 → **±29.47**.
벽 판정면은 |29.5| 인데 걸레받이가 0.4 나 튀어나와 있어 **벽에 붙어 서면 캐릭터가 걸레받이 안에
박혀 보였다.** 화면에서 읽히는 건 두께가 아니라 세로면(높이 1.8)이라 얇게 해도 선은 그대로다.

### 2. 🔴 개발이 쓸 노드 경로 계약 — **관절 피벗**

종전에는 메시가 전부 `Body` 밑에 평평하게 놓여 있었다. 그 상태로 다리를 돌리면
**엉덩이가 아니라 다리 한가운데를 축으로** 돌아 다리가 몸에서 빠져나간다.
움직여야 할 관절마다 **basis 가 단위행렬인 빈 `Node3D`** 를 관절 위치에 두고 메시를 매달았다.

#### 계약 표 — 이 경로와 부호는 아트가 보증한다

| 피벗 경로 | Body 기준 위치 | 밑에 달린 것 | 주 회전축 |
|---|---|---|---|
| `$Body/Neck` | (0, 1.14, 0) | 머리·모자·눈·눈동자 | x (끄덕), y (좌우 보기) |
| `$Body/ShoulderL` | (-0.27, 1.06, 0) | ArmL, HandL | **x** (앞뒤 흔들기) |
| **`$Body/Wand`** ★ | ( 0.27, 1.06, 0) | ArmR, HandR, Rod(마법봉), Muzzle | **x** (팔 들어올리기) |
| `$Body/Wand/Rod` | (0.12, 0, -0.4) | Stick, Tip | x (손목 스냅) |
| `$Body/HipL` | (-0.115, 0.53, 0) | LegL, AnkleL, FootL | **x** (다리 차기), z (벌리기) |
| `$Body/HipL/AnkleL` | (0, -0.46, 0) | FootL | **x** (발끝 들기) |
| `$Body/HipR` | ( 0.115, 0.53, 0) | LegR, AnkleR, FootR | 〃 |
| `$Body/HipR/AnkleR` | (0, -0.46, 0) | FootR | 〃 |
| `$Body/AimArrow` | (0, 0.03, 0) | RailL, RailR, Point | (회전 안 함 — 아래 3절) |

**★ `Body/Wand` 를 오른쪽 어깨 피벗으로 겸용한 이유 — 여기가 제일 중요하다.**
`Player.gd` 가 `$Body/Wand/Muzzle` 을 참조한다. 어깨 피벗을 새로 끼워 넣으면 그 경로가 깨진다.
그래서 **Wand 노드 자체를 어깨 관절 위치로 옮기고** 오른팔·오른손·마법봉을 그 밑에 넣었다.
- **경로 `$Body/Wand/Muzzle` 은 그대로다. 개발이 고칠 코드가 없다.**
- **Muzzle 의 최종 위치도 한 자리도 안 바뀐다** (Body 기준 `(0.2652, 0.7492, -0.8974)`).
- 덕분에 **`$Body/Wand.rotation.x` 한 줄로 팔+손+마법봉이 통째로** 올라간다 —
  사용자가 콕 집어 요구한 「팔을 위로 올렸다가 내리는 모션」이 이 값 하나로 나온다.
- 이름이 실제 역할(어깨)과 다른 건 인정한다. **개명 금지 규칙이 우선이라 그렇게 했다.**

#### 회전 부호 규칙 (전 관절 공통, 단위행렬 basis 라 섞을 일 없다)

```
rotation.x 양수 → 매달린 것이 앞(-Z)쪽으로 돈다.  다리는 앞으로 차고, 팔은 앞→위로 올라간다.
rotation.z 양수 → +X(캐릭터 오른쪽)으로 벌어진다.
rotation.y 양수 → 위에서 봤을 때 반시계.
```

#### ⛔ 쓰면 안 되는 것 / 대체 수단

- `$Body.rotation.x` — `_tick_flip()` 이 덤블링에 쓰고 매 프레임 0 으로 되돌린다. **애니메이션에 못 쓴다.**
- `$Body.rotation.y` — `_face()` 가 쓴다. 못 쓴다.
- **상하 바운스/스쿼시는 `$Body.position.y` 로 해라.** 코드가 안 건드리는 자리다.
- **가슴(chest) 피벗은 못 만들었다.** 만들면 `Body/Wand` 가 Body 의 직계 자식이 아니게 돼
  `$Body/Wand/Muzzle` 이 깨진다. 상체 기울임이 꼭 필요하면 `Neck` + 양 어깨를 같이 돌려라.
- 덤블링이 **발밑(y=0)을 축으로** 돈다. 몸 가운데(y≈0.85)를 축으로 돌리고 싶으면
  Body 를 돌리면서 `position.y` 로 보정해야 한다. 같은 이유로 아트가 노드를 못 끼워 준다.

#### 아트가 제안하는 수치 (그대로 써도 되고 조정해도 된다)

**걷기** — `move_speed 6.0`, 보폭 ≈ 0.62m → 다리 한 주기 ≈ 0.84초.
`phase += (수평속도 / 0.62) * TAU * delta` 로 위상을 굴리면 속도에 맞춰 자동으로 빨라진다.

| 노드 | 값 |
|---|---|
| `HipL.rotation.x` | `deg_to_rad(26) * sin(phase)` |
| `HipR.rotation.x` | 위상 +π (반대 다리) |
| `AnkleL/R.rotation.x` | `deg_to_rad(12) * sin(phase - 0.7)` (착지 직전 발끝 들림) |
| `ShoulderL.rotation.x` | `deg_to_rad(20) * sin(phase + π)` (다리와 대각) |
| `Wand.rotation.x` | `deg_to_rad(7) * sin(phase)` — **마법봉을 들었으니 오른팔은 작게** |
| `Body.position.y` | `0.045 * abs(sin(phase))` (두 걸음에 두 번 튄다) |
| `Neck.rotation.x` | `deg_to_rad(3) * sin(phase * 2)` |

**점프/공중**: `HipL/R.x = -14°`(다리 뒤로 모음), `AnkleL/R.x = +18°`, `ShoulderL.x = -40°`(팔 위로),
`Wand.x = +25°`. 착지 순간 `Body.position.y` 를 -0.09 → 0 으로 0.12초 스쿼시.

**스킬 시전** (`cast_time` 0.28~1.10초, `t` = 0→1 진행률) — 사용자가 요구한 모션:

| 구간 | 동작 |
|---|---|
| t 0 → 0.55 | `Wand.rotation.x` **0° → +72°** (팔+마법봉 위로 번쩍) · `ShoulderL.x -25°` · `Neck.x +6°` |
| t 0.55 → 0.78 | **정지(anticipation hold)** — 여기서 멈춰야 다음 동작이 세게 보인다 |
| t 0.78 → 1.0 | `Wand.rotation.x` **+72° → -18°** (내리치기, 오버슛) · `Rod.rotation.x` 를 **반대로** -20°→+10° 얹으면 손목 스냅이 생긴다 |
| 발사 후 0.14초 | `Wand.rotation.x` -18° → 0° 복귀 |

`ease_out_cubic` 으로 올리고 `ease_in_quart` 로 내리쳐라. **올릴 때 느리고 내릴 때 빠르면** 「탁」 하고 꽂힌다.
`cast_time` 이 짧은 스킬(0.28초)은 위 비율을 그대로 압축하면 된다 — 정지 구간이 짧아도 리듬은 남는다.

### 3. 조준 방향 표시 — `$Body/AimArrow`

사용자 요구: 「스킬이 날아가는 방향을 화살표나 이런 걸로 보이게」.

#### 노드 경로

```
$Body/AimArrow            Node3D          (0, 0.03, 0)
  ├ $Body/AimArrow/RailL  MeshInstance3D  왼쪽 레일 (BoxMesh 0.13 x 0.02 x 2.269, -7.5도)
  ├ $Body/AimArrow/RailR  MeshInstance3D  오른쪽 레일
  └ $Body/AimArrow/Point  MeshInstance3D  화살촉 (PrismMesh 1.05 x 1.4, 꼭짓각 41도)
```

**개발이 코드로 할 것**: 켜고 끄기(`$Body/AimArrow.visible`) · 시전 중 강조 · 덤블링 중 끄기.
**방향 회전은 코드가 필요 없다** — `Body` 밑에 달아서 `_face()` 가 Body 를 돌리면 저절로 따라 돈다.
즉 이 화살표는 언제나 `Player.aim_direction()` 과 **정확히** 같은 방향을 가리킨다.
⚠ 단, `_tick_flip()` 이 덤블링 때 `Body.rotation.x` 를 돌리므로 **그때는 화살표도 같이 돈다.**
`if _flip_left > 0.0: $Body/AimArrow.visible = false` 한 줄만 넣어 달라.

#### 왜 「가운데 한 줄 화살표」가 아니라 「레일 두 줄 + 떨어진 촉」인가

**카메라가 -32° 고정이라 북쪽(-Z)을 보면 바닥 화살표가 캐릭터 몸에 통째로 가린다.**
실제로 화면 세로 각도를 계산했다(카메라는 플레이어 기준 (0, 5.21, 5.94), 정면 -32°):

| 대상 | 화면 세로각 |
|---|---|
| 캐릭터 발밑 | -9.17° |
| **모자 꼭대기** | **+2.00°** |
| 바닥에 누운 2.9m 화살표 끝 | +1.63° ← **모자보다 낮다 = 완전히 가려진다** |

그래서 세 가지를 했고, 셋 다 렌더로 검증했다:

1. **레일을 몸통 바깥(±0.78m)으로 뺐다.** 캐릭터 실루엣 밖이라 어느 방향에서도 안 가린다.
2. **레일을 앞으로 7.5° 모았다.** 평행 두 줄은 「골대」로 읽혔다 — 모아야 방향이 생긴다.
3. **화살촉을 4.5m 앞에 뒀다**(화면 +5.6°, 모자보다 3.6° 위). 머리 위로 확실히 넘어간다.

**시행착오 기록 (다시 밟지 말 것)**
- 촉을 폭 1.72 / 길이 0.95(꼭짓각 84°)로 잡았더니 **화살이 아니라 지붕**으로 읽혔다.
  → 1.05 × 1.4(꼭짓각 41°)로 좁고 길게.
- 촉을 3.3~4.0m 로 당겼더니 모자에 붙어 **천막(정자)** 으로 읽혔다. → 4.5m.
- 레일 끝과 촉 밑변을 붙였더니 바깥선이 한 줄로 이어져 또 천막이 됐다.
  → **0.5m 를 일부러 띄웠다.** 이 틈이 「레일 / 촉」을 두 물체로 갈라 준다.

**⚠ 알려진 손해**: **정남향(카메라 쪽)일 때 화살촉이 화면 아래 스킬바 뒤로 빠진다.**
바닥 지시자를 카메라 쪽으로 눕히면 원근이 커져서 생기는 구조적 문제고,
북쪽 가독성(4.5m 이상 필요)과 남쪽 가독성(3.7m 이하 필요)이 **정면충돌**한다.
남쪽은 캐릭터 얼굴과 마법봉이 정면으로 보여 방향이 이미 자명하므로 **북쪽을 우선**했다.
신경 쓰이면 개발이 `$Body/AimArrow.scale.z` 를 0.55~1.0 으로 줄이면 된다(카메라 쪽을 볼수록 짧게).

#### 색 — 왜 「차가운 흰색」인가

- `mat_aim_rail` : unshaded · `Color(0.78, 0.88, 1.0, 0.30)`
- `mat_aim_head` : unshaded · `Color(0.88, 0.94, 1.0, 0.50)`

1. **투사체 색은 유저가 아무 색이나 고른다.** 특정 색상(hue)을 쓰면 그 색 스킬을 쓸 때
   조준선과 투사체가 서로를 잡아먹는다. **흰색은 상대 색이 없다.**
2. 바닥(0.44,0.38,0.31 따뜻한 나무)·러그(0.42 회색)와는 **명도**로 갈린다.
   살짝 푸른 기를 넣어 따뜻한 바닥 위에서 "물체"가 아니라 "빛"으로 읽히게 했다.
3. **`shading_mode = unshaded`** — 그림자(책상 밑·침대 옆)에 들어가도 밝기가 안 변한다.
   조준선이 어두운 데서 사라지면 쓸모가 없다.
4. **`emission` 을 안 썼다.** 글로우 문턱(1.3)을 넘기면 조준선이 번져서
   **마법 이펙트 전용으로 남겨 둔 글로우**를 조준선이 나눠 갖는다.

**개발에게 추천(선택)**: 재질이 `surface_material_override` 로 노드마다 독립이므로
시전 중에 `Point` 의 albedo 를 **그 슬롯의 skill_color** 로 갈아끼우면
「지금 이 색 스킬이 이쪽으로 나간다」가 한 번에 읽힌다. 알파는 0.5 유지 권장.

### 4. 킬 임팩트 연출 제안 — 「쿵」의 설계

화면 흔들림은 개발이 코드로 넣는다. 아트가 정하는 것은 **얼마나 · 어떤 곡선 · 무엇을 더 얹느냐**다.

#### 세기의 기준선 먼저

카메라 거리 7m, 세로 FOV 70° → 화면에 보이는 세로 높이 **9.80m**.
즉 카메라를 **0.10m 옮기면 화면 높이의 1.02%** 다. 이걸 자로 쓴다.

- 1% 미만 → 안 보인다. 넣으나 마나.
- **1.5 ~ 3%** → 「쿵」. 여기가 정답 구간.
- 4% 이상 또는 0.6초 이상 → **멀미.** 이 게임은 카메라가 고정각이라
  플레이어가 시점으로 보정할 수단이 없다. 다른 게임보다 상한이 낮다.

#### 흔들림 스펙 (총 0.35초)

| 요소 | 값 |
|---|---|
| 흔들 대상 | **`$CamPivot/SpringArm3D/Camera3D.position`** (로컬 x/y). SpringArm 의 벽 충돌 보정을 안 건드린다 |
| ① 방향 펀치 | 피격자 방향(화면 투영)으로 **0.20m**(2.0%). 0.045초 `ease_out` 으로 나갔다가 0.11초 `ease_out_back`(살짝 오버슛)으로 복귀 |
| ② 노이즈 떨림 | 진폭 **0.10m**, **22Hz**, `A × (1-t)^2.2` 감쇠, **0.28초**. 서로 나눠떨어지지 않는 두 주파수(예: 22Hz·31Hz)를 섞어야 주기적으로 안 보인다 |
| ③ FOV 킥 | `70 → 73.5` 를 0.05초, `→ 70` 을 0.20초 `ease_out`. **「쿵」을 실제로 파는 건 이거다** — 세상이 앞으로 확 다가온다 |
| ⛔ 회전(roll) | **넣지 마라.** 「화면 위쪽이 언제나 북쪽」이 이 게임 카메라 설계의 전제다. 롤은 그걸 깬다 |
| 다중 킬 | trauma 를 1.0 으로 **clamp**. 0.15초 안에 두 명 죽어도 두 배로 안 흔들린다 |

곡선은 Squirrel Eiserloh 식으로: `trauma` 를 저장하고 **흔들림 ∝ trauma²**,
`trauma -= 3.5 * delta`. 제곱이라 끝이 부드럽게 죽어서 「멈추다 만」 느낌이 안 난다.

#### 흔들림 말고 더 얹을 것 — 우선순위 순

1. **히트스톱 (제일 중요, 제일 쌈)** — `Engine.time_scale = 0.05` 를 **0.07초**.
   흔들림이 **재생 재개 순간에 터지도록** 배치하면 체감이 두 배가 된다.
   ⚠ 반드시 실시간 기준으로 풀어야 한다(`process_mode = ALWAYS` 타이머 또는 스케일 안 걸린 delta).
   안 그러면 시간이 안 돌아온다.
2. **피격자 백색 섬광** — **전체화면 플래시는 넣지 마라**(고정 카메라에서 너무 폭력적이다).
   대신 죽는 대상의 재질 `emission` 을 **백색 energy 6.0** 으로 0.06초.
   글로우 문턱(1.3)을 넘으므로 **여기서 블룸이 터진다.** 글로우를 마법용으로 아껴 둔 이유가 이것이다.
3. **바닥 충격파 링** — 죽은 자리 발밑에 납작한 링(토러스 또는 스케일한 판) 하나.
   지름 **0 → 3.0m 를 0.30초**, 알파 0.9 → 0, 두께도 같이 얇아짐.
   **-32° 부감은 바닥 링을 가장 예쁘게 보여주는 각도다.** 이 카메라가 공짜로 주는 연출이니 꼭 써라.
4. **파편** — 시체를 **8~12개 박스**로 터뜨린다. 위쪽으로 치우친 랜덤 임펄스 3~6m/s + 회전,
   0.9초에 걸쳐 축소·페이드. 조각 크기 0.2~0.4m 가 이 맵 스케일에서 잘 읽힌다.
5. **비네트 펄스**(선택) — 화면 가장자리를 0.25초간 12% 어둡게. 시선을 가운데로 모은다.
   **화면 전체 색조 변경은 하지 마라** — 투사체 색이 유저 마음대로라 어떤 색은 묻힌다.

### 1. 조사 — 「무엇이 타격감을 만드는가」

읽은 것과, 거기서 **원리로** 뽑아낸 것. (출처는 9절에 모아 뒀다)

#### 1-A. 원리 넷

**① 타격감은 「사건의 개수」가 아니라 「사건의 경계」다.**
Vlambeer 의 *Art of Screenshake* 가 나열하는 30여 개 트릭 중 절반 이상이
**시작과 끝을 만드는 장치**다 — 총구 섬광(발사에 시작을 준다) · 임팩트 이펙트(명중에 끝을 준다) ·
잔재(permanence, 지나간 자리를 남긴다) · 슬립(hit pause, 명중에 길이를 준다).
지금 우리 투사체는 **시작도 끝도 없다.** 태어나고 사라질 뿐이다. 여기가 진짜 병목이다.

**② 「즉시 켜고 천천히 끈다」가 임팩트의 문법이다.**
juice 자료들이 공통으로 말하는 tweening 규칙 — 임팩트는 **어택 1~2프레임 / 릴리즈 5~10프레임**이다.
반대로(천천히 켜고 즉시 끄면) 「터졌다」가 아니라 「부풀었다 사라졌다」로 읽힌다.
→ 아래 모든 플래시가 **0.02초 켜고 0.09~0.14초 끄는** 이유다.

**③ 히트스톱은 0.04~0.08초.**
조사 결과가 일관된다 — 3~12프레임(0.05~0.2초) 범위 안에서 **40~80ms** 가 "무게를 파는" 구간이고,
0.05초 미만은 안 느껴지고 0.1초 초과는 **랙으로 오해된다.**
격투게임은 약/중/강을 8F/12F/16F 로 나눠 **세기의 위계**를 만든다.
→ 지난 리포트에 내가 쓴 **「히트스톱 0.07초」는 조사로 확인됐다.** 그 값을 그대로 쓴다.
   다만 **적용 범위를 좁힌다** — 4-D ② 참고.

**④ 소리가 타격감의 절반이고, 그중에서도 저역(bass)이다.**
juice 자료가 반복하는 문장: 게임플레이 사운드는 "full" 해야 하고 **베이스와 미드를 강조**하라.
Vlambeer 목록에도 "more bass in sound design" 이 독립 항목으로 들어 있다.
→ 5절에서 다룬다. **지금 소리가 0개라는 건 타격감의 절반이 아예 없다는 뜻이다.**

#### 1-B. 우리에게 **적용 가능한 것**

| 트릭 | 왜 우리에게 맞나 |
|---|---|
| 총구 섬광 | 마법봉 끝 = 발사 지점이 이미 실루엣으로 확립돼 있다. 얹을 자리가 있다 |
| 임팩트 이펙트 · 링 | **-32° 부감은 바닥 링을 가장 예쁘게 보여주는 각도다.** 카메라가 공짜로 주는 연출 |

| 트릭 | 왜 우리에겐 안 되나 |
|---|---|
| **탄을 키운다 / 빠르게 한다 / 연사를 올린다** (Vlambeer 목록의 절반) | ⛔ **전부 밸런스 값이다.** `Balance.derive()` 가 속도 12~28m/s · 사거리 8~34m · 판정 폭을 계산한다. 손맛을 위해 여기 손대면 **폭 정규화 대원칙이 깨진다.** 손맛은 **연출로만** 만든다 |
| 카메라 롤(회전 흔들림) | ⛔ 「화면 위쪽이 언제나 북쪽」이 이 게임 카메라 설계의 전제다. 롤은 그걸 깬다(지난 리포트와 동일 판단) |
| 화면 전체 플래시 · 화면 색조 변경 | ⛔ 투사체 색이 **유저 마음대로**라 어떤 색은 묻히고 어떤 색은 튄다. 고정 카메라에선 특히 폭력적이다 |
| 화면 흔들림을 **모든 명중**에 | ⛔ 5:5 · QWER 4슬롯 · 산탄 최대 7발이다. 전부 흔들면 **킬 흔들림이 특별해질 자리가 없고**, 그냥 어지럽다 |
| `Engine.time_scale` 히트스톱을 **모든 명중**에 | ⛔ 산탄 7발이 동시에 맞으면 0.49초 정지다. 게다가 5:5 에서 시간 정지는 **나 말고 9명의 시간도 멈춘다** |
| 탄 껍질(shell casing) · 총기 반동 애니메이션 | ⛔ 총 게임이 아니다. 기획서가 못박았다 |

> **한 줄 요약**: Vlambeer 목록에서 **「게임 규칙을 바꾸는 항목」은 전부 버리고
> 「보이고 들리는 것만 바꾸는 항목」만 가져왔다.** 우리의 형평성 검산이 전부 살아 있어야 하기 때문이다.

### 2. 🔬 실측 — 목업을 만들어 렌더해서 확인했다

숫자만으로는 연출을 못 정한다. `Arena.tscn` 에 **임시 목업**(잔상 트레일 · 총구 섬광 ·
명중 플래시 · 명중 링 · 지면 예고 링)을 세워 3회 렌더하고 **확인 뒤 원본으로 되돌렸다**
(813행 · `load_steps=88` 복원 확인).

#### 실측 결론 다섯 — 이 값들은 눈으로 확인한 것이다

**① 🔑 색은 「가산(add)」이 아니라 「혼합(mix)」에서만 살아남는다.**
진한 청보라(0.28, 0.2, 0.95)로 전부 다시 렌더해 봤다.
- **혼합으로 깐 잔상** → 채도가 그대로. 나무 바닥·회색 러그 어디에서도 「그 색 스킬」로 읽힌다.
- **가산으로 깐 헤일로·링** → 회색 러그 위에서 **연보라로 떠서** 무슨 색인지 안 읽힌다.

→ **역할 분담을 여기서 확정했다.**
  **유저가 그린 그림과 그 잔상 = 혼합(색의 주인) / 플래시·링 = 가산(밝기 담당).**

**② 가산 플래시의 한가운데는 어떤 색을 넣어도 흰색으로 탄다.**
싸우지 말고 **이용한다** — 흰 코어를 **일부러** 따로 두되 **0.03초만** 쓰고,
색 헤일로를 0.14초까지 남긴다. 눈에 남는 잔상은 **색 쪽**이 된다.
헤일로 알파는 0.85 → **0.55**로 내렸다. 0.85 는 헤일로 자체가 흰색으로 타 버렸다.

**③ 잔상 간격은 그림 크기(span)의 0.55배면 뭉치고, 0.95배면 흩어진다.**
0.55배 → 삼각형 5장이 **하나의 통짜 원뿔**로 뭉쳐 「빠르다」가 아니라 「크다」로 읽혔다.
0.75배로 벌리니 장수가 세어지면서 streak 으로 읽혔다. 옆(+X)으로 나가는 궤적에서는
0.75가 살짝 성겼다. → **0.65 × span** 채택.

**④ 발사 등(FireLight)을 세게 켜면 자기 섬광을 자기가 덮는다.**
range 5.0 / energy 4.0 으로 켜 봤더니 반경 5m 짜리 웅덩이가 생겨 화면을 먹고,
**섬광 quad 가 그 빛에 묻혀 흰 점으로 쪼그라들었다.** → **range 4.0 / peak 2.4**.
순서를 기억할 것 — **읽히는 건 quad, 등은 「방이 반응한다」만 담당한다.**

**⑤ 카메라 쪽(+Z)으로 쏴도 트레일은 죽지 않는다.** (걱정했던 것)
빌보드라 잔상이 화면에서 겹칠 줄 알았는데, **원근 때문에 가까운 잔상이 커져서** 오히려 잘 읽혔다.
옆(+X)·앞(-Z)·카메라쪽(+Z) 세 방향 다 렌더해서 확인했다. **방향 예외 처리 필요 없다.**

### 3. 🔴 이번 설계의 중심 판단 — 「그림이 읽히는 것」 vs 「속도감」

이게 사용자가 나에게 맡긴 저울이다. 내 답은 이것이다.

> **그림 자체는 절대 건드리지 않는다. 속도감은 「그림 주변」이 아니라 「그림의 과거」로 만든다.**

즉 **잔상(afterimage) 트레일** — 지나간 자리에 **같은 그림을 반투명으로 떨어뜨린다.**

왜 이게 저울의 정답인가:

| 수단 | 그림에 무슨 짓을 하나 |
|---|---|
| 진행방향 스트레치 | 그림을 **찌그러뜨린다.** 유저가 그린 별이 타원이 된다 |
| 회전(스핀) | 유저가 그린 글자·화살표가 **거꾸로 선다.** 그림은 「위」가 있는 기호다 |
| 파티클 꼬리 | 그림 위에 **다른 그림을 얹는다.** 그림이 안 보인다 |
| 속도선·모션블러 | 그림을 **뭉갠다** |
| **잔상 트레일** | **그림을 N번 더 보여준다. 속도감을 만들면서 가독성이 오히려 올라간다** |

**잔상은 이 게임에서 유일하게 「가독성과 속도감이 같은 방향인」 수단이다.**
나머지 모든 연출은 둘이 반대 방향이라, 그것들은 **그림이 아닌 곳**(총구·명중 지점·바닥·빛·소리)에만 쓴다.

파생 규칙 세 개:
- **그림은 언제나 알파 1.0, 채도 100%, 크기 고정.** 유일한 예외가 태어나는 0.055초(팝)다.
- **그림 위에는 아무것도 안 얹는다.** 후광은 **뒤에**, 플래시는 **앞뒤 끝(발사·명중)에만.**
- **그림을 돌리는 유일한 경우** = 길쭉함 태그의 진행방향 정렬(4-C ⑤). 이건 「찌그러뜨림」이 아니라
  「창을 창끝 방향으로 든다」라서, 오히려 그림의 뜻을 살린다.

### 4. 국면별 설계 — 무엇을 · 얼마나 · 언제

기준자 (지난 리포트에서 계속 쓰는 것):
**카메라 7m · 세로 FOV 70° → 화면에 보이는 세로 높이 = 9.80m. 카메라 0.10m = 화면의 1.02%.**
캐릭터 키 1.7m. 투사체 그림 폭 `span` = 판정 폭(`Balance` 기준 **1.01 ~ 3.91m**).
속도 12~28m/s · 사거리 8~34m · 발동 0.12~1.10초 · 쿨 0.6~9.0초.

#### 4-A. 국면 ① 발사 직전(예고) — 「모으는 게 보여야 한다」

**모든 스킬에 발동 시간(0.12~1.10초)이 있다. 그게 이미 예고 창이다.** 지금은 그 창이 비어 있다.
`t` = 발동 진행률 0→1 (`Player._tick_skill` 의 `_cast_left` 로 이미 계산돼 있다).

| 대상 | 값 | 곡선 |
|---|---|---|
| `$Body/Wand/Rod/Tip` 재질 `emission_energy_multiplier` | 3.2 → **9.0** | **`t²`** |
| `Tip` 노드 `scale` | 1.0 → **1.7** | `t²` |
| `$Body/Wand/Rod/Tip/ChargeLight.light_energy` ★신설 | 0 → **2.5** | `t²` |
| `$Body/Wand/Muzzle/ChargeMotes` ★신설 | `emitting = true` (발사 순간 false) | — |
| `Tip`·`ChargeLight`·`ChargeMotes` 색 | **그 슬롯의 skill_color** | — |

**왜 `t²` 인가**: 선형으로 올리면 「밝아지는 중」이라는 정보만 있고 **언제 터질지가 안 실린다.**
제곱이면 앞은 잔잔하고 **끝에서 확 밝아진다** = 「지금 나온다」가 몸으로 읽힌다.

**⚡ 예고의 진짜 장치 — 「터지기 직전의 딥(dip)」**
`_cast_swing()` 이 이미 t=0.55~0.78 을 **정지(anticipation hold)** 로 잡아 뒀다.
그 정지가 끝나는 **t=0.78 에서 Tip 밝기를 0.75배로 한 번 떨어뜨렸다가** 내리치기와 함께 터뜨려라.
**밝기 대비가 클수록 터짐이 세 보인다.** 2프레임짜리 딥 하나가 밝기를 두 배 올리는 것보다 세다.

**차징(`DELIVERY_CHARGE`) 전용** — 차지율 `c`(0.2~1.0)가 위 `t` 자리를 대신한다.
`c = 1.0` 도달(완충)은 **반드시 별도의 신호**를 줘야 한다. 안 그러면 유저가 언제 놓을지 모른다:
- `Tip.scale` **1.7 → 2.0 → 1.75** (0.12초, `ease_out_back` 오버슛)
- 흰 섬광 **0.05초** (`Flash/Core` 만 켠다. 색 헤일로는 안 켠다 — 완충은 색 정보가 아니라 시각 신호다)
- 반경 **0.9m 링이 0으로 수축** 0.12초 — 「다 모였다」의 시각 언어
- 그 뒤 `Tip.scale` 을 **1.75 ↔ 1.9, 4Hz** 로 숨쉬게 둔다. 「지금 계속 완충 상태」

**기모으기(`DELIVERY_GROUND`) 전용** — `GROUND_TELEGRAPH = 0.8초` 예고 원.
- 바닥 링: 지름 = `유효명중폭 × GROUND_RADIUS_MULT × 2`, 테두리 **0.08m**, 스킬 색, 가산, 알파 **0.45**
- 안쪽 채움 원반: 알파 **0.18**, **0 → 꽉 참을 0.8초에 걸쳐** (= **남은 시간이 곧 채움률**. 시계다)
- 마지막 **0.15초**: 링만 **흰색으로 2번 점멸**(0.0375초 주기). 「지금 떨어진다」
- ✅ 렌더로 확인했다 — **-32° 부감에서 바닥 링은 이 게임에서 가장 잘 읽히는 도형이다.**
  목업에서 가장 선명했던 요소가 이거였다.

#### 4-B. 국면 ② 발사 순간 — 「총구 섬광 · 반동 · 카메라 킥」

`t=0` = 투사체가 스폰되는 프레임.

**아트가 `Player.tscn` 에 미리 심어 뒀다.** 개발은 켜고 끄기만 하면 된다:

```
$Body/Wand/Muzzle/Flash          Node3D          visible=false 로 잠들어 있음
$Body/Wand/Muzzle/Flash/Halo     MeshInstance3D  quad 1.7m · 가산 · 빌보드 · 라디얼 그라디언트
$Body/Wand/Muzzle/Flash/Core     MeshInstance3D  quad 0.62m · 가산 · 흰색
$Body/Wand/Muzzle/FireLight      OmniLight3D     energy=0 · range 4.0
$Body/Wand/Muzzle/ChargeMotes    CPUParticles3D  emitting=false
$Body/Wand/Rod/Tip/ChargeLight   OmniLight3D     energy=0 · range 3.5
```

| 요소 | 값 | 타이밍 |
|---|---|---|
| `Flash.visible` | true | t=0 |
| `Halo` 재질 `albedo_color` | **rgb = 스킬 색**, a = **0.55** → 0 | a 는 t=0.02 부터 **0.11초** `ease_out` |
| `Halo` `scale` | 1.0 → **0.55** | 같은 구간 |
| `Core` 재질 알파 | **0.95 → 0** | **0.03초.** ⚠ 흰색이므로 **길게 끌면 스킬 색을 먹는다** |
| `Core` `scale` | 1.0 → 0.5 | 0.03초 |
| `Flash` `rotation.z` | **매 발사마다 `randf() * TAU`** | 연사할 때 같은 그림 반복을 깬다 |
| `FireLight.light_energy` | **0 → 2.4 → 0** | 즉시 켜고 **0.10초** `ease_out` |
| `FireLight.light_color` | **스킬 색** | — |
| `ChargeMotes.emitting` | **false** | t=0 (모으기 끝) |

**크기 근거**: 헤일로 quad 1.7m → 그라디언트 감쇠 때문에 **눈에 보이는 지름 약 0.85m**
= **캐릭터 키의 절반.** 1.5m 로 줄였더니 손에 묻혀 안 보였고, 그 이상은 얼굴을 가린다. (렌더 확인)

**⚠ 색 규칙 (사용자가 콕 집은 제약: 「연출이 hue 를 먹으면 안 된다」)**
- `Core` 는 **영원히 흰색이다.** 개발이 여기에 스킬 색을 넣지 마라. 흰색은 상대 색이 없어서
  **어떤 hue 와도 안 싸우고**, 어두운 스킬 색(진남색 등)이어도 「터졌다」가 반드시 보인다.
- `Halo` 와 `FireLight` 만 스킬 색이다.
- 이 분담이면 **밝기는 흰색이, 색 정보는 헤일로와 트레일이** 나눠 갖는다. 서로 안 먹는다.

**반동(recoil)** — 「쐈다」를 몸이 말하게 한다. `_cast_swing()` 이 이미 `-18°` 오버슛을 준다. 거기에:

| 대상 | 값 | 타이밍 |
|---|---|---|
| `$Body.position.y` | 0 → **-0.05** → 0 | 0.04초 내려가고 0.09초 `ease_out` 복귀 |
| `$Body.position` (수평) | 조준 반대방향으로 **0.06m** → 0 | 0.04초 / 0.12초 `ease_out` |

⚠ `Body.position` 은 코드가 안 건드리는 자리다(`_face` 는 `rotation.y`, `_tick_flip` 은 `rotation.x`).
**단 `position.y` 는 걷기 바운스와 겹친다** — 지난 리포트가 바운스를 `Body.position.y` 로 지정했다.
**둘을 더해서 쓰라**(`Body.position.y = 걷기바운스 + 반동`). 한쪽이 다른 쪽을 덮어쓰면 조용히 사라진다.

**카메라 킥** — Vlambeer 는 「쏜 방향의 **반대로** 카메라를 찬다」고 한다. 그대로 쓴다.

| 항목 | 값 |
|---|---|
| 대상 | `Camera3D.h_offset / v_offset` (`ScreenShake.gd` 가 이미 쓰는 자리) |
| 방향 | **조준 방향을 화면에 투영한 것의 반대** |
| 세기 | **`0.06 + 0.05 × (데미지슬라이더/100)` m** → **0.06~0.11m = 화면의 0.6~1.1%** |
| 타이밍 | **0.03초** `ease_out` 으로 나갔다가 **0.09초** `ease_out` 복귀. 총 0.12초 |

**⚠ 지난 리포트의 「1% 미만은 안 보인다」를 여기서 정정한다.**
그 기준은 **일회성 사건**(킬)의 것이다. 발사는 **내가 키를 누른 직후에, 반복해서** 일어나므로
플레이어가 이미 대기 중이라 **역치 아래여도 몸이 등록한다.** 대신 상한을 낮게 잡아야 한다 —
연사하면 누적되기 때문이다. 그래서 킬(2.0%)의 **절반 이하**로 묶고, 데미지에 비례시켜
**싼 스킬은 가볍고 R은 묵직하게** 위계를 만든다(1-A ③ 「세기의 위계」 원리).

#### 4-C. 국면 ③ 비행 중 — **여기가 이번 작업의 심장이다**

##### ⓪ 먼저 할 것 — **빌보드를 끄고 basis 를 직접 준다** (다른 항목의 전제)

지금 `sprite.billboard = BILLBOARD_ENABLED` 다. 빌보드는 **노드의 회전을 통째로 무시**하므로
정렬·팝·미세 흔들림을 **하나도 못 얹는다.**

**그런데 우리 카메라는 고정각(yaw 0° / pitch -32°)이다 → 카메라 basis 가 상수다.**
따라서 **빌보드를 끄고 카메라 basis 를 그대로 복사하면 결과가 픽셀 단위로 같다.** 시각 변화 0, 자유도 +3.

```gdscript
# 상수. 한 번만 구해서 캐시하면 된다(카메라가 고정각이라 절대 안 변한다).
var cam_basis := get_viewport().get_camera_3d().global_basis
# roll = 화면 안에서 그림을 돌리는 각(라디안), s = 팝/펄스 배율
sprite.billboard = BaseMaterial3D.BILLBOARD_DISABLED
sprite.global_basis = cam_basis * Basis(Vector3(0, 0, 1), roll) * Basis.from_scale(Vector3(s, s, 1.0))
```

> 🔴 **함정**: 지금 `Projectile._ready()` 가 `basis = Basis.looking_at(_dir)` 로 **몸을 진행 방향으로 돌린다**
> (캡슐 판정을 눕히려고). 스프라이트는 그 자식이라 **빌보드를 끄는 순간 그 회전을 상속받는다.**
> 반드시 **`global_basis`(로컬 아님)로 매 프레임 덮어써라.** 안 그러면 그림이 옆으로 누워 날아간다.

##### ① 🥇 잔상 트레일 (afterimage) — **하나만 넣는다면 이것**

지나간 자리에 **같은 그림을 반투명으로** 떨어뜨린다. 3절에서 설명한 저울의 답이다.

| 항목 | 값 |
|---|---|
| 간격 | **`spacing = 0.65 × span`** (m) ← 렌더로 잡았다. 0.55는 뭉치고 0.95는 흩어진다 |
| 투하 주기 | **`interval = clamp(spacing / speed, 0.016, 0.12)`** (초). 속도가 빠를수록 촘촘 |
| 수명 | **`life = 4 × interval`** → **언제나 잔상 4장이 살아 있다** (크기·속도와 무관하게 일정) |
| 알파 | **`0.45 × (1 - age/life)`** — 선형 |
| 크기 | **`lerp(1.0, 0.70, age/life)`** |
| 블렌드 | **혼합(mix). ⛔ 가산 금지** — 2절 ① |
| 색·텍스처 | **투사체와 완전히 동일**(같은 `ImageTexture` 를 재사용. 새로 안 만든다) |
| 회전 | 투하 순간의 투사체 roll 을 그대로 고정. 이후 안 돈다 |

> 🔴 **잔상은 투사체의 자식이면 안 된다.** 부모가 움직이면 같이 끌려가서 트레일이 안 생긴다.
> **투사체의 부모(world)에 붙이고** 스스로 `queue_free` 하게 하라.
> (`Player._spawn()` 이 투사체를 형제로 붙이는 것과 같은 이유·같은 자리)

**비용**: 투사체당 살아있는 노드 4개. 산탄 7발이면 28개. 텍스처는 재사용이라 0. GL Compatibility 무관.

**렌더 확인**: 삼각형(뾰족한 그림 가정) 잔상 4장이 **각각 셀 수 있게 남으면서 하나의 흐름**으로 읽혔다.
선두의 삼각형은 완전히 선명했다. **진한 청보라로도 나무 바닥·회색 러그 양쪽에서 다 읽혔다.**

##### ② 태어나는 팝 (spawn pop) — 「나타났다」를 「발사됐다」로 바꾼다

| 항목 | 값 |
|---|---|
| `scale` | 0.35 → **1.12** → 1.0 |
| 타이밍 | 0 → 1.12 를 **0.055초** `ease_out_back`, 1.12 → 1.0 을 **0.05초** |

⚠ **물리는 건드리지 마라.** 태어나는 순간부터 `speed` 는 정상값이다. 커지는 건 **겉모습만**이다.
(속도를 램프시키면 `max_distance` 도달 시간이 바뀌어 회피 타이밍이 흔들린다 = 밸런스 침범)

##### ③ 코어 후광 (뒤에 까는 것 — **그림 위에는 아무것도 안 얹는다**)

| 항목 | 값 |
|---|---|
| 형태 | 라디얼 그라디언트 quad 1장, **그림 뒤에** (`render_priority` 를 그림보다 낮게) |
| 지름 | **`span × 1.6`** |
| 색·블렌드 | 스킬 색 · **가산** · 알파 **0.32** |
| 펄스 | 알파 `0.32 + 0.10·sin(2π·11·t)` / 크기 `1.0 + 0.07·sin(2π·11·t)` |

**11Hz 인 이유**: 60fps 에서 한 주기 5.5프레임. 이보다 빠르면 **깜빡임(스트로브)** 으로 보이고,
느리면 「숨 쉰다」가 아니라 「크기가 변한다」로 보인다. 11Hz 는 「에너지가 지직거린다」의 구간이다.

##### ④ 기존 `OmniLight3D` 를 살린다 (지금은 상수라 아무 정보도 안 준다)

| 대상 | 값 |
|---|---|
| `light_energy` | `1.6 × (1 + 0.22·sin(2π·11·t))` ← **후광과 같은 위상** |
| `omni_range` | `max(span × 2.5, 3.0)` ← 지금은 `radius×5` 인데 **큰 스킬일수록 방을 더 밝혀야** 맞다 |

##### ⑤ 회전 — **판단: 「그림을 계속 돌리는 것」은 하지 않는다**

유저가 그린 그림은 **「위」가 있는 기호**다. 글자·화살표·얼굴을 그리면 스핀은 그걸 파괴한다.
대신 **태그별로** 이렇게 나눈다:

| 태그 | 회전 | 근거 |
|---|---|---|
| **길쭉함** | **진행 방향에 정렬**(아래 공식) | 창을 그렸으면 **창끝이 앞을** 봐야 한다. 지금은 통나무처럼 옆으로 난다 |
| 뾰족함 · 둥긂 | **`±5°`, 7Hz 흔들림** | 「살아 있다」만 주고 절대 뒤집히지 않는다 |
| 흩어짐 | **자유 회전 가능** (탄마다 다른 속도로, `±180°/s`) | 덩어리에는 「위」가 없다. 여기만 스핀이 안전하다 |

**길쭉함 정렬 공식** (그림의 주축을 화면 안에서 진행방향에 맞춘다):

```gdscript
# 1) 그림의 주축 각 (마스크 좌표: x 오른쪽, y 아래). Balance._elongation() 의 sxx/syy/sxy 와 같은 값이다.
theta = 0.5 * atan2(2.0 * sxy, sxx - syy)
# 2) 진행 방향을 화면에 투영한 각
phi   = atan2(dir.dot(cam_basis.y), dir.dot(cam_basis.x))
# 3) 스프라이트 roll (텍스처 v 가 뒤집혀 있어 theta 의 부호가 그대로 더해진다)
roll  = phi + theta
```
- **적용 조건**: `Balance.analyze_mask()` 의 `elongation >= T_ELONGATION_LONG(2.5)` 일 때만.
  (신장도가 1에 가까우면 주축이 정의되지 않아 값이 널뛴다)
- 스폰 팝 구간(0.055초) 동안 `roll` 을 0에서 목표값으로 보간해서 넣어라. 툭 튀면 눈에 걸린다.
- ⚠ **`sxy/sxx/syy` 를 `Balance` 가 지금 안 돌려준다.** 두 방법 중 하나:
  (a) `analyze_mask()` 반환에 `axis_rad` 키 추가를 기획 담당에게 요청, 또는
  (b) `Projectile` 이 이미 `_drawn_box()` 로 마스크를 훑으므로 **거기서 같이 계산**(추가 비용 0).
  → **(b) 를 권한다.** 밸런스 파일을 안 건드리는 쪽이 안전하다.

##### ⑥ ⛔ 하지 않기로 한 것 (그리고 그 이유)

| 수단 | 왜 안 하나 |
|---|---|
| 진행방향 스트레치(늘이기) | **그림을 찌그러뜨린다.** 유저가 그린 원이 타원이 된다. 이 게임의 정체성을 파는 값이다 |
| 파티클 꼬리(불꽃·연기) | 그림 **위에** 다른 그림이 얹힌다. 잔상이 같은 일을 하면서 가독성은 안 깎는다 |

| 항목 | 값 |
|---|---|
| 값 | `Engine.time_scale = 0.05` 를 **0.07초** |
| ⚠ 해제 | **반드시 실시간 기준** — `process_mode = ALWAYS` 타이머 또는 스케일 안 걸린 delta. 아니면 시간이 안 돌아온다 |
| 발동 조건 | **적을 쓰러뜨린 그 한 발만.** `take_damage()` 가 「죽였다」를 돌려줄 때만 |
| 디바운스 | **0.30초에 한 번.** 이미 도는 중이면 무시 |
| 산탄 | 마지막 일격을 넣은 **한 발만** 발동 |
| 배치 | 지난 리포트대로 — **해제되는 순간에 흔들림·FOV 킥·파편이 동시에 터지게.** 체감이 두 배가 된다 |

**왜 일반 명중엔 안 되는가 (셋 다 치명적이다)**
1. 산탄 최대 7발 → **0.49초 정지.** 게임이 멎는다.
2. **5:5 다.** `Engine.time_scale` 은 내 화면만 멈추는 게 아니라 **10명의 시간을 멈춘다.**
3. 1-A ③ 의 「세기의 위계」 — 모든 명중이 멈추면 **킬이 특별해질 자리가 없다.**

**대신 쓸 것 = 「홀드」.** 위 타임라인의 **0.000~0.040 헤일로 최대 유지**가 그것이다.
시간을 안 멈추면서 **시각적으로만 0.04초 얼어붙는다.** 1-A ②의 "hold key poses" 원리 그대로다.
비용 0, 멀티 안전, 산탄 7발이 겹쳐도 그냥 밝아질 뿐이다.

### 5. 소리 — 「지금 당장 할 수 있는 최소한」

**현황: 오디오 파일 0개 · `AudioStreamPlayer` 0개.** 조사가 말하는 「타격감의 절반」이 통째로 없다.

#### 5-A. 🔑 결론 — `AudioStreamGenerator` 가 아니라 **`AudioStreamWAV` 를 코드로 굽는다**

Godot 에서 파일 없이 소리를 내는 길은 둘이다.

| 방법 | 판정 |
|---|---|
| `AudioStreamGenerator` + `push_frame()` 실시간 합성 | ⚠ **권하지 않는다.** 매 프레임 버퍼를 채워야 하고, 버퍼가 마르면 **지직거린다**(Godot 문서가 명시한 트레이드오프). 폴리포니·3D·피치 변조를 전부 손으로 짜야 한다 |
| **`AudioStreamWAV.data` 에 PCM 을 계산해 넣고 `AudioStreamPlayer3D` 로 재생** | ✅ **이걸 쓴다.** 게임 시작 때 **한 번** 굽고 끝. 런타임 비용 0, 언더런 없음, `pitch_scale`·폴리포니·3D 감쇠·버스 이펙트가 **전부 공짜로 딸려온다.** 그러면서 **오디오 파일은 여전히 0개** |

```gdscript
const RATE := 22050  # 효과음엔 충분하다. 44100 의 절반 비용

func bake(dur: float, fn: Callable) -> AudioStreamWAV:
    var n := int(RATE * dur)
    var data := PackedByteArray(); data.resize(n * 2)
    for i in n:
        var v: float = clampf(fn.call(float(i) / RATE), -1.0, 1.0)
        data.encode_s16(i * 2, int(v * 32767.0))
    var w := AudioStreamWAV.new()
    w.format = AudioStreamWAV.FORMAT_16_BITS
    w.mix_rate = RATE
    w.stereo = false
    w.data = data
    return w
```

> 🔴 **주파수 스윕의 함정**: `sin(TAU * f(t) * t)` 는 **틀린다**(f 가 변하면 위상이 튄다).
> **위상을 누적**해라 — `phase += TAU * f(t) / RATE` 하고 `sin(phase)`.
> 이걸 틀리면 「휘융」이 아니라 「지지직」이 난다.

#### 5-B. 지금 당장 구울 소리 넷

| 소리 | 합성 | 길이 |
|---|---|---|
| **발사** | 사인 스윕 **880 → 140Hz**(지수) · 포락선 `exp(-t/0.030)` **＋** 화이트노이즈 버스트 `×0.45·exp(-t/0.012)` | **0.14초** |
| **명중** | 화이트노이즈 `×0.6·exp(-t/0.045)` **＋ 저역 사인 스윕 160 → 70Hz** `×0.8·exp(-t/0.090)` | **0.18초** |
| **킬** | 명중음 **＋** 사인 스윕 **300 → 55Hz** `×0.9·exp(-t/0.16)` | **0.40초** |
| **차징** | 삼각파 **220 → 660Hz** 상승 · 볼륨 `t/dur` 램프 · 끝에 `×1.15` 부스트 | **0.50초** 굽고 `pitch_scale = 0.5/cast_time` 으로 늘임 |

**저역 사인이 명중음의 주인공이다.** 조사 1-A ④ — bass 를 강조하라.
노이즈만 넣으면 「치익」이고, 저역을 얹어야 「퍽」이 된다.

#### 5-C. 소리에 정보를 싣는다 (공짜로 얻는 것)

| 규칙 | 값 |
|---|---|
| **스킬 크기 → 피치** | `pitch_scale = lerpf(1.30, 0.70, range_pt / 100.0)` — 작은 스킬은 「틱」, 큰 스킬은 「쿠웅」 |
| **변주** | 그 위에 매번 `× randf_range(0.94, 1.06)`. Vlambeer 의 반복 방지 원리 |
| 자기 발사음 | **`AudioStreamPlayer`(비공간)** — 내 스킬은 언제나 또렷해야 한다 |
| 남의 발사음·명중음 | **`AudioStreamPlayer3D`** — 위치·거리가 그대로 정보가 된다(5:5 에서 특히) |
| 클리핑 방지 | `AudioServer` 로 **"SFX" 버스 + `AudioEffectLimiter`** 를 코드로 추가. 산탄 7발 동시 발사가 안 깨진다 |

**소리를 하나만 넣는다면 「명중음」이다.** 발사는 이미 화면에서 팔이 내리쳐지지만,
명중은 **화면 반대편 끝에서 일어나서 시선이 거기 없을 수 있다.** 소리는 시선이 필요 없다.
